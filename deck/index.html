Mayfly

A live preview for every pull request.
It sleeps when nobody is looking.

Reviewers click one link and see the change running. Idle previews cost almost nothing, and they are removed when the pull request closes.

Business overview

Mayfly1
Open with the one-line promise: every pull request gets its own running preview; it sleeps when idle and is deleted when the PR closes. Mayfly is a working product you can run today.

The problem

Reviewing code is easier when you can see it run. Preview environments are not.

Reviewers can't see the change

A diff shows code, not behaviour. Designers, product managers and QA wait for a shared staging server, then ask which branch is on it.

Always-on previews cost money

One environment per pull request means servers running day and night for pages that are opened a few times, then forgotten.

Nobody cleans up

Old previews pile up after merges. They use memory and disk, and may keep serving code that was never meant to stay public.

The solution

One link per pull request, managed from open to delete.

  1. 1

    PR opens

    A GitHub webhook tells Mayfly. It builds the PR's own Dockerfile at the exact commit.

  2. 2

    Link appears

    A comment and a check on the PR carry the preview link.

  3. 3

    Idle: sleeps

    No visits for a set time and the app stops. The link stays valid.

  4. 4

    Visit: wakes

    A "Waking up" page shows at once, then the preview loads itself.

  5. 5

    PR closes: gone

    Merge or close removes the container and image. A lifetime limit removes the rest.

Works with a repository Dockerfile, or Mayfly writes one for common stacks (Next.js, Vite, Node, Flask and others). The app must listen on its port and not need root.

Why it is cheap

You pay for the minutes a preview is actually being used.

7 up, 0 awake

What our own demo instance showed on 19 November: seven previews available to open, none of them consuming compute.

A single instance and a handful of previews. Not a benchmark.

  • Sleep when idle

    The app stops after a set time with no visits (20 seconds in the sample setup). The next visit wakes it.

  • Lifetime limit

    Every preview expires on a schedule (7 days in the sample setup), by repository rule or admin extension.

  • Limits per developer and in total

    Cap live previews overall and per person, so one busy branch cannot fill the server.

  • Budget and cost view

    Awake hours by preview, day and month, a monthly budget that can pause new previews, CSV export and optional weekly email.

What is built

A working product, not a mock-up.

Board and admin

Live board with awake or asleep state, filters, a setup checklist for first preview, command palette, and admin actions: wake, sleep, extend, destroy.

Review on the preview

Mark a spot on a preview and comment on it. A review page with a comments panel, plus a PR comment and check with the link.

Settings per repository

Size, encrypted variables, optional sandbox database, smoke-check pages, and a screenshot compare against production.

Cost and schedules

Budget with pause at the limit, cost by repository or team, awake-hours schedules for demos, and a one-off wake before a review.

Operations

Health & ops page, audit CSV, migrate pack and restore, chat alerts, and CPU and memory per preview.

Installable app

Installs from the browser on phone and desktop, with iOS Add-to-Home-Screen guidance. An Android APK build is included.

Safe by design

Pull-request code is untrusted, so previews are locked down.

Locked-down containers

Non-root user, read-only filesystem, all capabilities dropped, no new privileges, limited memory, CPU and processes.

Docker behind a filter

Mayfly never holds the Docker socket. A proxy allows only containers, images and builds, and refuses exec, volumes and networks.

Signed webhooks

A missing or wrong GitHub signature is rejected and creates nothing.

Admin access

Every change needs the admin token. Sign-in cookies hold an expiry and a signature, never the token.

Encrypted variables

Preview variables are encrypted with AES-256-GCM and never sent back to the browser.

Optional preview password

A team password for preview links, with lock-out after repeated wrong guesses. Admins are never asked.

Honest limit: the Docker filter works by endpoint, so it cannot stop a deliberately privileged container. For a public server, run Docker rootless or build on a separate host.

Be upfront about the limit; it is in our own README. The recommended production setup is rootless Docker or Sysbox, or a separate build host.

Where we are

Working product today. Here is what it still needs.

Working now

  • Real pull-request builds (Dockerfile or auto-written for common stacks)
  • Sleep, wake, expiry and clean-up on close or merge
  • GitHub comments, checks, signed webhooks and failure help
  • Board, admin, cost, schedules, review, settings and Health & ops
  • Several hosts by sharding repositories (each owns its Docker)
  • One-script AWS setup and automated tests on GitHub

Before it is a business

  • No shared preview pool across machines (shard repos instead)
  • Runtime logs stay in memory for the life of the preview, not on disk
  • Public board is read-only but open; no private-board mode
  • Single admin token; no team accounts or roles yet
  • No customer pilots or usage data yet
  • Dockerfiles that need BuildKit-only features do not build

Who it is for

Small and mid-size engineering teams on GitHub that review work across developers, designers and QA — with a Dockerfile, or a common stack Mayfly can write one for.

How it could be sold

Self-hosted and free to run. A managed, hosted plan for teams that do not want to run servers. Support and compliance features for larger customers.

What we would measure

Preview infrastructure cost saved against always-on previews, review turnaround time, and share of pull requests that get a preview.

Pricing, market size and competitor comparison are intentionally left out. They need customer conversations first. Fill them in after the first pilots.
